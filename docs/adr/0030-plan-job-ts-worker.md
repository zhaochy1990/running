# Plan generation and structural adjustment run as a Plan Job in a dedicated TS worker

Status: accepted

## Context

Generating or structurally adjusting a season training plan or a weekly plan runs the TS Planning Kernel, which takes 3–5 minutes (roughly 18 structured LLM calls plus up to 3 artifact-revision loops for the season plan). This cannot run inside a single chat turn, which today is a synchronous `POST` with a 12-second client timeout. The legacy path — the Python BFF's in-process generation route (`POST /users/me/master-plan/generate`) backed by an in-memory thread job runner and a generator that writes drafts to Azure Table — is lost on process restart, and the draft lifecycle there is split from the MySQL reads that serve the current plan. This ADR records the replacement: an async **training plan job (训练计划任务)** executed by a dedicated TypeScript worker.

## Decisions

- **Trigger — Pattern X.** The Coach (TS Deep Agent) only *drafts a plan proposal (计划提案)* — a structured kernel request plus a Chinese summary — and never executes a generation side effect. The deterministic coach endpoint enqueues the job after the athlete confirms via a card in chat; the same endpoint re-validates the proposal with the kernel's zod schema (the client payload is never trusted) and validates the weekly adjustment window (current/future week only). Enqueue is idempotent on `(user, idempotency_key)`; there is no per-user concurrency cap (multiple candidates may generate concurrently).
- **Job id lives in chat history.** The confirm action is performed by the chat layer (not the worker): it appends a message carrying `job_id` and `job_type` to the same LangGraph thread, so on reopen/another device the history still renders the generation card. The worker does not write chat and does not emit a conversation receipt on completion — the job stays business-pure and isolated.
- **Dedicated TS worker, own queue.** A standalone TypeScript worker process consumes its own work/retry/poison queues (not the Go worker's), dispatches by `job_type` (generate/adjust × season/weekly), streams the kernel with node-level updates, reports monotonic stage/progress, and writes nothing to chat.
- **Go stays the single writer of plan tables.** The worker writes plan drafts only through Go internal endpoints (internal-token-authenticated), and never touches the plan tables directly — preserving the ADR 0006 single-writer invariant. Drafts are inserted as new rows (insert-only, idempotent) and are never auto-activated; enabling is explicit (transaction: archive the current active, activate the chosen draft, sibling drafts stay draft) and discarding archives a draft.
- **Multi-draft is now allowed.** This deliberately narrows the weekly plan `status_slot` uniqueness index to constrain only `active` (at most one active per user/week); draft rows no longer occupy a slot and may be many. The master plan already permits multiple draft rows (only its active is unique). This supersedes the stance in ADR 0024 that the draft/generation/confirm APIs are not migrated; drafts for both plan kinds now live in MySQL with the same draft/active/archived lifecycle.
- **No automatic retry.** Business failures (contract violations, and the kernel's non-completed decisions such as goal conflict, safety block, quality-gate failure, needs-clarification) are terminal `failed` with a stable error code and are not retried; only transient infra errors go through the retry queue (≤ 2 attempts), and transient LLM-level errors surface through the SDK's own HTTP retries. A worker crash is covered by message redelivery (≤ 2 attempts) plus a heartbeat-based stale-`running` reconcile.
- **Retire the Python in-process generation path.** Once both the miniprogram and web frontends are switched, remove the Python generation routes, the in-memory job runner, and the master/weekly generators. Azure legacy draft reads are retained and migrated separately.

The TS worker owns the plan-job status table in the coach persistence database; `master_plan` / `weekly_plan` schema and writes remain Go-owned.
