# Go `cmd/api`: activity read endpoints (`GET /api/{user}/activities`, `GET /api/{user}/activities/{labelId}`)

The Go `cmd/api` has ported the write/onboarding/watch surface (ADR 0013, 0018) but no *activity read* surface. We add the two endpoints that back the web/mobile activity views as a coexisting port with contract parity: `GET /api/{user}/activities` (filtered, paginated list plus per-month summaries) and `GET /api/{user}/activities/{labelId}` (one activity's full detail, with an opt-in `?include=timeseries`). They shadow the FastAPI routes in `stride_server/routes/activities.py`. The endpoints are implemented and marked `goReady: true` in the BFF strangler manifest, but the manifest keeps `upstream: 'python'` — the browser is not yet cut over (a separate routing decision).

## Decision

- **Two endpoints emit the exact Python JSON** they shadow, so a later browser cutover is pure routing. The list body is `{total, offset, limit, activities[], monthly_summaries{}}`; the detail body is `{activity, stride_training_load, laps[], segments[], zones[], timeseries?, linked_scheduled_workout}` in that key order.
- **A sibling `activityRoutes` registrar** mounts on the shared authed group (mirroring `userRoutes`, ADR 0013), reusing the internal-token / user-JWT auth. The `internal/api` package stays free of GORM behind a narrow **`ActivityStore`** port (six read methods) satisfied by `*storage.Store`; the SQL lives in `internal/storage/activity_read.go` per the repo's SQL-ownership rule.
- **The `:user` param route coexists with the static `/api/users/:uid/pipelines` + `/api/users/me/*` routes.** Verified against gin v1.12.0: the static segment wins where it matches and the param branch handles everything else — no registration panic, no mis-dispatch.
- **Two auth tiers, tenant-scoped.** `authorizeUser` allows a user-tier caller only when the path `{user}` equals its JWT `sub` (else `403`); an internal-tier caller may read any user. A denied request never touches the store. A missing detail row → `404 {"error":"Not found"}`.
- **Presentation helpers are centralized in a new `internal/apifmt` package** (metre→km at 2 dp, `HH:MM:SS` duration with `int()` truncation, `m:SS/km` pace, UTC→Shanghai ISO, `round(x,1)`, and strength `seg_name`). This is the single source for the format logic the Python `stride_core`/`deps` helpers own, so list, detail, and lap/segment rows format identically. Pure unit tests cover the edge cases (nil/zero → `"—"`/`None`-equivalent).
- **`monthly_summaries` replicates `_activity_monthly_summaries_for_visible_months`:** for every Shanghai month present on the *page*, `{activity_count, total_run_km (1 dp), duration_s}`, with `total_run_km` summing **run activities only** while `activity_count` counts all rows matching the list filter. The map is **always present** (`{}` when the page is empty), never null.
- **Shanghai month/day is computed in SQL and Go, and they agree byte-for-byte.** MySQL uses `DATE_FORMAT(date + INTERVAL 8 HOUR, '%Y-%m')` / `DATE(date + INTERVAL 8 HOUR)`; the Go side adds a fixed `+8h` before formatting. This is safe because `storage.Open` forces the session to UTC (`parseTime=true, loc=UTC, time_zone='+00:00'`), so `activities.date` scans as a UTC instant. An integration test asserts the boundary: `2026-03-31 20:00Z` (`2026-04-01 04:00` Shanghai) buckets to `2026-04`.
- **The running/strength predicates are literal, sorted, constant SQL** built from `RUN_SPORT_IDS` + normalized `sport`/`sport_name` value sets — no user input is interpolated, so there is no injection surface. They are shared by the `sport_category` list filter and the monthly run-distance aggregate.
- **`?include=timeseries` gates the heavy array (M1 mobile contract).** Without it, `ActivityTimeseries` is never queried and the `timeseries` key is **omitted** (`omitempty` on `*[]T`); with it, the series is downsampled `step = max(1, len/1000)` (taking indices `0, step, 2·step, …`, matching Python `all_ts[::step]`) and always rendered as an array (`[]` when empty).
- **JSON null/empty invariants match Python:** nullable numeric/text columns are pointers (missing → `null`); `laps`/`segments`/`zones` and `reasons` are always arrays (`[]`, never null); `pauses` defaults to `[]`; `route_thumb` is opaque passthrough gated by `json.Valid` (invalid/absent → `null`); `stride_training_load` and `linked_scheduled_workout` are always present (`null` when absent).

## Divergences from Python (deliberate)

- **`zones` is projected from `activity_watch_zones` (watch-reported), not the calibrated `zones` table** the Python endpoint reads. The Go store does not hold calibrated per-activity zones; the watch-reported buckets are the closest available shape (ordered `zone_type, zone_index`, dropping the raw `zone_type_raw`). This is a **semantic gap**, not just a schema rename — the numbers can differ from Python. It closes when the calibrated zone projection is ported.
- **`linked_scheduled_workout` is always `null`.** The `scheduled_workout` authoring table is not part of the watch-synced MySQL store (Storage-scope rule); the multi-variant fallback link cannot be resolved here. The field is kept in the contract for shape parity.
- **Commentary fields are omitted** from both list and detail. `activity_commentary` is an authoring artifact written by the local/reader environments, out of scope for this read port.
- **Segment rows omit `exercise_type`/`exercise_name_key`** (Python includes them as extra keys); the frontend consumes only `seg_name` + `mode`, so the resolved display name plus raw mode are emitted and the raw keys dropped.
- **`route_thumb` is byte-passthrough**, so an insignificant-whitespace difference from Python's decode-then-re-encode is possible; the value is never inspected.

## Consequences

- **Manifest is `goReady:true` but still `upstream:'python'`.** The two routes in `frontend/server/src/routing/api-routes.ts` are flagged Go-ready (with ADR-0019 comments) so a cutover is a one-line `upstream` flip per route once the divergences above are acceptable for the browser. Until then, no user traffic hits the Go handlers.
- **`cmd/api` already reads the watch-data tables** (established by ADR 0018); this port extends that to `activities`/`laps`/`activity_watch_zones`/`timeseries`/`activity_training_load`, all owned by the one canonical MySQL schema (ADR 0006).
- **Cutover is gated on the zone semantic gap.** Flipping `upstream:'go'` for the detail route before the calibrated-zone projection lands would silently change the zone numbers the UI shows. The list route has no such gap and can cut over independently.
- **`internal/apifmt` is now the home for API presentation format.** Future ported read endpoints (dashboard, laps, splits) must reuse it rather than re-implementing metre→km / pace / duration formatting, per the no-duplicate-helpers rule.
- **Tests are layered:** pure `apifmt` unit tests; `internal/api` handler-contract tests against a fake `ActivityStore` (auth tiers, param parsing/clamping, null/empty invariants, `include` toggle, downsample); and MySQL-gated `internal/storage` integration tests (filter/order/paginate, monthly summaries incl. the TZ boundary, date window, laps-by-type, zone order, training-load presence) — all green against MySQL 8.4.
