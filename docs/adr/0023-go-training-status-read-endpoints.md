# Go `cmd/api`: training-status read endpoints (`/health`, `/hrv`, `/stride/zones`, `/stride/training-load`, `/pmc`)

The Go `cmd/api` has ported the write/onboarding/watch surface (ADR 0013, 0018, 0020) and the activity read surface (ADR 0019), but not the metrics read surface that backs the `/training-status` web page and the fatigue/PMC + plan-adjust pages. We add five coexisting read endpoints with contract parity, shadowing the FastAPI routes in `stride_server/routes/health.py` (`/health`, `/hrv`, `/pmc`) and `stride_server/routes/stride.py` (`/stride/zones`, `/stride/training-load`):

- `GET /api/{user}/health` — daily-health rows + HRV snapshot block + per-day HRV trend + `rhr_baseline`
- `GET /api/{user}/hrv` — per-day HRV detail + latest-reading summary
- `GET /api/{user}/stride/zones` — STRIDE calibration threshold + pace/HR training zones
- `GET /api/{user}/stride/training-load` — calendar-continuous daily PMC series (STRIDE load) + projected current
- `GET /api/{user}/pmc` — vendor ATI/CTI/TSB PMC **and** the STRIDE-load PMC block, combined

All five emit the frontend-consumed contract of the Python routes they shadow, with the deliberate divergences documented below. They are marked `goReady: true` in the BFF strangler manifest but keep `upstream: 'python'` — no browser traffic is cut over (a separate routing decision, per ADR 0019).

## Decision

- **Five endpoints emit the frontend-consumed contract** — the same keys, null-vs-absent semantics, and envelope (trend / summary / vendor+stride PMC blocks) the TypeScript interfaces in `frontend/src/api.ts` declare — via curated DTOs, so a later browser cutover is pure routing. This mirrors ADR 0019's curated-DTO stance rather than a literal `SELECT *` echo: JSON key **order** is not reproduced (it is immaterial to JS/Go consumers, and Python's own order comes from SQLite physical column order — e.g. `daily_health.provider` sits mid-row because the Garmin columns are `ALTER TABLE`-appended — which the TS interfaces already don't match). All data already lives in the canonical MySQL schema (ADR 0006) and is written by the onboarding-compute pipeline (ADR 0015): `daily_health`, `dashboard`, `daily_hrv`, `running_calibration_snapshot`, the split `running_calibration_pace_zone` + `running_calibration_hr_zone`, and `daily_training_load`. The endpoints normally read persisted metrics plus presentation; the sole exception is `/stride/training-load`, whose calendar-continuity projection recomputes ATL/CTL in memory as described below without writing MySQL.
- **Two sibling registrars mirror the Python file split**: `healthRoutes` (`/health`, `/hrv`, `/pmc`) and `strideRoutes` (`/stride/zones`, `/stride/training-load`), each mounting on the shared authed group (like `userRoutes`/`activityRoutes`), reusing the internal-token / user-JWT tiers and `authorizeUser` tenant scoping (path `{user}` must equal the JWT `sub` for a user-tier caller; internal-tier may read any user).
- **The `internal/api` package stays free of GORM** behind two narrow read ports — `HealthStore` and `StrideStore` — satisfied by `*storage.Store`; the SQL lives in `internal/storage/health_read.go` + `stride_read.go` per the repo's SQL-ownership rule. `/pmc` reads both `daily_health` (vendor) and `daily_training_load` (STRIDE), so `HealthStore` exposes the training-load reads it needs; the shared "latest usable daily load" read is one `*storage.Store` method both ports call (no duplication).
- **Presentation reuses `internal/apifmt`** (ADR 0019). A new helper mirrors Python `_pace_fmt` exactly — `int(round(1000/speed_mps))` → `"M:SS"` — so zone paces are computed from the stored speed columns and match byte-for-byte regardless of how the stored pace-seconds were rounded.
- **`/stride/zones` maps the two split zone tables back onto Python's single-table output.** Pace `lower_pace`/`upper_pace` come from the slower/faster speed edges (`min_speed_mps`/`max_speed_mps`); HR `lower_bpm`/`upper_bpm` use `int()` truncation of the float bpm columns; both lists are sorted into physiological order (recovery → easy → marathon → threshold → interval → repetition). A user with no snapshot returns `{"threshold": null, "pace_zones": [], "hr_zones": []}`.
- **`/stride/training-load` returns a calendar-continuous series through Shanghai today.** The read projection starts from the earliest usable persisted row available in the requested window (`coverage_status ∈ {complete, partial, rest_confirmed}`), then recomputes every following day through today. Missing or `unknown` dates become read-only `rest_assumed` rows with zero dose and the canonical `internal/compute/trainingload` 7/42-day ATL/CTL decay; observed rows retain their dose and audit metadata. Projected rows are not written to MySQL, and a later sync can replace them with canonical computed rows. `/pmc` keeps its persisted-series contract. `readiness_reasons` is the decoded `readiness_reasons_json` list (empty on null/invalid).
- **The calibration snapshot read is pinned to the current model version.** `/stride/zones` (threshold + zones + `calibration_id`) and `/health` (`rhr_baseline`) read through `LatestRunningCalibrationSnapshotForVersion(user, calibration.ModelVersion, asOf)`, which mirrors the Python `calibration_connector.fetch_latest`: `WHERE algorithm_version = ?` (so a superseded snapshot left by a prior model bump can't shadow the current-version baseline) `AND as_of_date <= ?` (`/health` passes today; `/stride/zones` passes no bound) `ORDER BY as_of_date DESC, id DESC`. The model version is sourced from the single-source `calibration.ModelVersion` constant and threaded in by the api layer so `internal/storage` stays free of a compute dependency.
- **`/pmc` reproduces the full combined Python contract** — `{pmc, summary, stride_pmc, stride_summary}`. The vendor half derives `tsb = cti − ati`, `tsb_zone`/`tsb_zone_label` from ACWR (`training_load_ratio`, falling back to `ati/cti`) rather than absolute TSB, and `ctl_ramp` = `cti − cti[i−7]`. The STRIDE half adds `chronic_load_ramp` (`chronic_load − chronic_load_7d_ago`), where the 7-days-prior chronic is a `LEFT JOIN` on `DATE_SUB(date, INTERVAL 7 DAY)`. `days` clamps to `[14, 365]` (`/health`/`/hrv` clamp `[1, 365]`, `/stride/training-load` clamps `[7, 365]`).
- **The metric date columns are Shanghai-local strings, not UTC instants.** `daily_health.date`, `daily_hrv.date`, and `daily_training_load.date` are already Shanghai calendar-day strings, so these endpoints do **no** timezone conversion — unlike `activities.date` (a UTC instant that readers shift +8h, ADR 0019). `/health` additionally normalizes its `health[].date` from `YYYYMMDD` (COROS) to ISO `YYYY-MM-DD` (mirroring `_normalize_health_date`); `/hrv` and `/pmc` echo their date columns raw, matching Python.

## Divergences from Python (deliberate)

- **`/stride/training-load` records omit the internal echo columns `calibration_id` and `computed_at`.** Python serves that route with `SELECT *` + `dict(row)`, so those two columns ride along; the TS `StrideTrainingLoadRecord` declares neither, and `computed_at` is a per-row write timestamp with no stable cross-runtime representation (SQLite `datetime('now')` text vs Go `DATETIME(6)`). The Go DTO emits only the consumed fields. (The `/pmc` stride block already uses an explicit column list in Python, so it has no such extras.)
- **The HRV preferred-provider-per-date dedup is intentionally not ported.** Python wraps `daily_hrv` reads in `HRV_PREFERRED_PER_DATE_SQL`, which collapses multiple provider rows on one date to a single row (garmin > coros > alphabetical). The product binds **exactly one watch data source per user** (see `CONTEXT.md` → 手表数据源), so `daily_hrv`/`daily_health` hold at most one row per date and Go reads them with a plain `ORDER BY date`. If the one-watch invariant is ever relaxed (or a provider switch produced a same-date collision), these reads would return the extra row — a latent gap to close by porting the dedup at that point.
- **`daily_training_load.acute_load/chronic_load/form` serialize as non-null numbers, never `null`.** The DB columns are nullable but the Go `DailyTrainingLoad` model types them `float64` (ADR 0015), so a NULL would scan to `0` rather than the `null` Python's `dict(row)` would emit. This is unreachable today — the compute pipeline always writes non-null values for these three (only `load_ratio`, correctly nullable, can be `null`) — but the DTO would diverge from the `number | null` TS type if a NULL ever landed. Closing it means making the model fields pointers, a change scoped to the compute pipeline, not this read port.

## Consequences

- **Manifest is `goReady:true` but still `upstream:'python'`** for all five routes (`frontend/server/src/routing/api-routes.ts`), so a cutover is a one-line `upstream` flip per route once parity is validated. Until then no user traffic hits the Go handlers.
- **The 自研 / 透传 boundary is expressed in the route layout, not by reshaping `/pmc`.** `/stride/*` carries STRIDE-computed metrics and `/health`+`/hrv` carry watch-passthrough fields (see `CONTEXT.md` → STRIDE 自研指标 / 手表透传字段). `/pmc` deliberately spans both for contract parity — splitting it into a vendor-only `/pmc` + a new `/stride/pmc` was considered and rejected, because the STRIDE-load PMC is already served by `/stride/training-load` (same table, same shape) and a second endpoint would duplicate it.
- **`internal/apifmt` gains a speed→pace helper** that is the single source for the `_pace_fmt` formula; future zone/pace ports reuse it rather than re-deriving `1000/speed` rounding.
- **Tests are layered** (per ADR 0019): pure `apifmt` unit tests for the new pace helper; `internal/api` handler-contract tests against fake `HealthStore`/`StrideStore` (auth tiers, `days` clamping, zone ordering + int/pace formatting, calendar-continuous projection and projected `current`, null/empty invariants, `/pmc` tsb-zone bands + ramps); and MySQL-gated `internal/storage` integration tests (windowing/order, latest-usable persisted-row filter, the `chronic_load_7d_ago` join, date normalization).
