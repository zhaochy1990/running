# Race item content folds onto the item row, and the item sync becomes a per-field merge

Status: accepted

Supersedes [ADR 0035](0035-race-calendar-admin-surface-and-sync-merge.md) for
the item level only; its event-level decisions stand unchanged.

## Context

ADR 0035 split the race model in two: the event (`race_calendar`) gained
provenance (`origin` + `admin_overrides`) and a per-field sync merge, while the
per-distance content went into a separate `race_item_content` table keyed by
`(race_event_id, item_name)`, and `race_calendar_item` kept being regenerated by
delete+insert on every 中国田协 sync.

That asymmetry costs the item level things the event level does not pay:

- **No override mechanism, only a full detach.** `race_calendar_item` has no
  `admin_overrides` column, so the admin surface upgrades the whole row to
  `origin='manual'` on *any* edit (`applyRaceItemUpdate`). An administrator
  filling in one start time detaches the item from the mirror permanently —
  every later upstream change to that name is ignored. ADR 0035's own rule for
  events (*key-field edits detach, other edits override*) cannot be expressed at
  the item level.
- **Content keyed by a name string is fragile.** Renaming an item needs a
  follow-up UPDATE to chase the content row, and the read path does a
  name→content map join on every request.
- **The two-row write leaks into the API.**
  `CreateRaceCalendarItemWithContent`,
  `UpdateRaceCalendarItemWithContent` (with its rename carry) and
  `MoveRaceContent`'s raw `INSERT ... SELECT` exist only to keep two rows in
  step.
- **A stale-item gap.** An event was protected at stale-delete time only if the
  *content table* held a row for one of its items; an item carrying just an
  admin-maintained entry field (a start time, say) provided no protection and
  was deleted along with its event.

The timing is the cheapest it will ever be: production is not live,
`race_item_content` holds zero rows, all 478 `race_calendar_item` rows are
`origin='sync'` with `start_time`/`entry_fee`/`quota` NULL, and the
runner-facing race calendar (#344 / #345) has not started.

## Decisions

- **One row per item.** `race_calendar_item` gains the ten content columns
  (`distance_km` … `photos`), `admin_overrides` and `content_stale`.
  `race_item_content` is dropped — unconditionally, since production is not
  live and the table carried no data.
- **The item sync becomes a per-field merge**, mirroring
  `ReplaceRaceCalendarYear`: upsert on `(race_event_id, name)`, keep the current
  value of every field named in the row's `admin_overrides`, take the upstream
  value for the rest. An `origin='manual'` item is neither refreshed nor
  deleted.
- **The sync writes only what upstream supplies.** 中国田协 gives an item's name
  and race-types token and nothing else, so `start_time` / `entry_fee` / `quota`
  and the ten content columns are absent from `raceCalendarItemUpsertCols`. The
  sync cannot blank an administrator's work even in principle — the same
  reasoning that keeps the event's six content sections out of
  `raceCalendarUpsertCols`.
- **Stale items survive on admin data.** An item the upstream no longer lists is
  deleted only if nothing admin-maintained is attached; otherwise it is flagged
  `content_stale` and kept, and the flag clears when the name is re-listed. The
  survivor test is `RaceCalendarItem.HasAdminData` — content, overrides, or one
  of the admin-maintained entry fields — which also closes the gap above: an
  event whose only admin data is one such item is now protected too.
- **`type` overrides are recorded server-side.** The item PATCH carries no
  `overrides` array. The item's only sync-managed field is recorded
  automatically, because a client that forgets to declare it must not lose the
  administrator's edit to the next sync; `reset_fields` stays, so a field can
  still be handed back to the mirror.
- **The API contract is unchanged.** `raceCalendarItemDTO` still nests `content`
  (null = no content yet), so the dashboard needs no change; the backend simply
  reads one row instead of joining two.

## Consequences

- `type` is the only item override today. Adding another sync-managed item field
  means listing it in **both** `RaceCalendarItemOverrideableFields` and
  `raceCalendarItemUpsertCols`.
- `RaceCalendarItem.HasContent` (the ten content columns) and `HasAdminData`
  (content + entry fields + overrides + detach) carry deliberately different
  meanings: the first is the content contract, the second the stale-survivor
  test.
- `MoveRaceContent` carries an item's admin data over **by name**, and recreates
  a source item the target does not have as `origin='manual'` — a rename that
  also changed the distance names drops no content.
- The new columns come from `AutoMigrateRaceCalendar`, which the worker also
  runs, while the `race_item_content` drop lives in `AutoMigrateRaceContent`
  (API side). The new `ReplaceRaceCalendarItems` needs the columns to exist, so
  the API must ship before (or with) the worker — they share one tag in
  `versions.env` and release together.
- The runner-facing surface (#344 / #345) can now read an item's course content
  straight off the item row, without the name join.
