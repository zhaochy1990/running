# Go `cmd/api`: Race Goal endpoints + `race_goal` MySQL table

ADR 0013 deferred the athlete's race/training-plan goal to "a separate future table owned by the training-plan setup work". This is that work. We port `POST/GET/PUT /api/users/me/training-goal` from the Python `stride_server` route (a single JSON envelope `{current, history≤5}` stored per-user in the Azure Blob content-store) to a **greenfield Go `cmd/api` + MySQL redesign**. It is not a parity port: we take the opportunity to drop the unused goal-type taxonomy, model the entity properly, and enrich it toward what the downstream master-plan generator already consumes. Following the ADR 0013 profile precedent, the endpoint ships `goReady:true` but the BFF route stays on Python — **the flip is deferred** (see Consequences).

## Decision

### Domain: Race Goal
- **Race goals only; the `type` enum is dropped.** The Python model carried `type ∈ {race, pb, fat_loss, health, maintain}`, but only `race` is ever modeled downstream (the master-plan generator, predictions, and the frontend intake all assume a race), and all five prod goals are `type:"race"`. The entity is the **Race Goal (赛季目标)**: a named target race, its date and distance, an optional target finish time, plus the athlete's weekly-availability preferences for training toward it.
- **At most one *active* Race Goal per athlete; archived goals are retained.** Setting a new goal archives the current active one. History is kept as an **audit trail** (provenance / future analytics / backfill) but is **not exposed via the API** — no consumer reads history today, so we don't ship a history read endpoint (YAGNI). The endpoint surface stays exactly `POST` (create + archive previous active) · `GET` (current active, or `404`) · `PUT` (edit the active goal in place).

### Fields (enriched toward `MasterPlanGoal`)
- Inherited: `race_date` (YYYY-MM-DD), `race_distance ∈ {5K,10K,HM,FM,trail}`, `race_name?`, `target_finish_time?` (`null` = finish-only), `weekly_training_days` (3–6), `available_time_slots?` (`{morning,noon,evening}`), `strength_willingness?` (`{yes,no,conditional}`).
- **Added `race_location?` and `race_timezone?` (default `Asia/Shanghai`)** to match the downstream `MasterPlanGoal` snapshot (`stride_core/master_plan.py`). The generator already reads `goal.location` / `goal.timezone` but the Python endpoint never persisted them, so today they silently resolve to `null` / the Shanghai default and an overseas race can't record its city or local timezone. Both stay optional so the S1 season-plan setup form (which doesn't collect them) still POSTs cleanly. `race_timezone` is the *race's* local zone (for countdown / race-day), semantically distinct from the user's day-bucketing zone; it is accepted as an opaque string (no strict IANA validation yet). Capturing these in the UI is a separate frontend-contract follow-up.

### Storage: one `race_goal` MySQL table (ADR 0006, GORM AutoMigrate)
- **Single table holding current + archived rows**, keyed by `goal_id` — not a current-table + history-table split. Columns: `goal_id` **`char(36)`** PK, `user_id` `varchar(64)`, `status ∈ {active,archived}`, the race + preference fields above, GORM-managed `created_at`/`updated_at`, and `active_flag`.
- **≤1 active enforced by MySQL nullable-unique.** `active_flag *int8` is `1` on the active row and `NULL` on archived rows, with a composite `UNIQUE(user_id, active_flag)`. MySQL unique indexes don't collide on `NULL`, so an athlete may have many archived rows but only one active — the constraint is enforced by the database, not just application logic. `active_flag` is **app-managed** (a nullable pointer, matching the house `*time.Time` style), not a generated column: GORM AutoMigrate (the ADR 0006 house rule) has no first-class generated-column support, and MySQL has no partial indexes (the Postgres way), so the nullable column is the standard mechanism.
- **All state transitions go through one transactional store method.** Create-and-archive flips the old active row (`status=archived`, `active_flag=NULL`) and inserts the new active row (`status=active`, `active_flag=1`) atomically, so `active_flag` can never drift out of sync with `status`. This is app-level state (not watch-synced), so it lives in its own MySQL table, never the watch DB (Storage-scope rule) — and the `cmd/api` container has no durable shared FS for the Python blob approach anyway.
- **`user_id` is `varchar(64)`** (matching the `user_profile` precedent, keyed off the JWT `sub`), while **`goal_id` is `char(36)`** — server-minted UUID4 for new goals (see re-mint below).

### Timezone helper
- The future-date guard (`race_date` must be strictly after **today in Shanghai**) uses the new single-source `internal/utils/timefmt.ShanghaiToday()` (ADR 0020), created and converged as a separate prep commit rather than adding another inline Shanghai copy.

### API shape / house patterns
- Handlers form a **sibling registrar** in `internal/api` (own store dep) mounted on the shared authed group, keeping the ADR 0012 `Service` focused — same structure as the ADR 0013 profile endpoints.
- **Validation parity**: binding/validation failures return `422` with a FastAPI-shaped `detail: [{loc, msg}]` array so the existing frontend field-error UX works unchanged. Registered `goReady:true`; committed swagger is regenerated (ADR 0014).

### Migration & flip (deferred — this task ships the plan + unrun tooling, not the cutover)
- **Mirror the ADR 0013 profile staging: build `goReady:true`, leave the BFF route on `python`.** Flipping the *writer* to MySQL is blocked on the same unsolved prerequisite as profile — Python consumers still read the goal from the blob, here **three required, consistency-gated readers**: master-plan generation (`routes/master_plan.py`), the master-plan adjustment gate (`master_plan_apply.py`, which 409s when the live goal's `goal_id`/`race_date`/`race_distance`/`target_time` disagree with the plan's embedded snapshot), and predictions (`routes/predictions.py`). Porting those readers (or dual-writing the blob) is separable flip-time work, out of scope here.
- **One-shot backfill script authored now but not run** (unit-tested against fixtures): migrate the 5 prod goals' `current` into `race_goal` rows (all `history=[]`, so nothing else to migrate). Three goals already carry UUID4 `goal_id`s and migrate verbatim.
- **Two seeded goals carry non-UUID slug ids** (`s1-2026-chengdu-fm`, `s1-2026-longkou-hm`). Because `goal_id` is `char(36)`, these are **re-minted to UUID4** at backfill time — and since `goal_id` is a referenced identity checked by the adjustment gate, the re-mint **also rewrites the embedded `goal.goal_id` in those two users' prod master-plan snapshots** so the gate keeps passing. The re-mint is **forward-only**: it does not rewrite the legacy blob, so the cutover is not cleanly reversible by flipping the route back (an accepted trade-off for a 5-user endpoint). The backfill therefore must run **only at flip time**, coordinated with the reader porting — running it while Python is still live would rewrite snapshots the blob-reading gate still validates against and 409 those two users.

## Consequences

- **The flip is a distinct future task** with its own prerequisites: port the three Python blob-readers (or dual-write the blob), run the backfill, flip the BFF route, and update the frontend contract (drop the `type:'race'` constant + stray `id?`, surface `goal_id`). Until then the Go endpoint is dormant behind the router table.
- **Forward-only migration.** Re-minting two `goal_id`s mutates generated-plan provenance and is not reversible via a route flip-back; the blob retains the old slugs. Deliberate, given the tiny user set.
- **Dual-store during coexistence.** While the route stays on Python, MySQL `race_goal` is written by nothing in prod; it becomes canonical only at flip. The Python blob remains the live store until then.
- **Downstream `location`/`timezone` are carried but unfed** until a UI collects them; the generator keeps applying its `Asia/Shanghai` default, exactly as today.
- **`char(36)` + re-mint over opaque `varchar(64)`.** We chose a uniform UUID column shape and paid for it with a prod master-plan-snapshot rewrite for two rows, rather than accepting mixed slug/UUID ids in the column.
