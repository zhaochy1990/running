# Weekly feedback belongs to a Shanghai calendar week

Status: accepted

Go stores weekly feedback in a separate MySQL `weekly_feedback` table keyed by `(user_id, week_start)`, where `week_start` is the full `YYYY-MM-DD` date of the Shanghai Monday derived from the API `week_name`. Feedback belongs to the natural week rather than any `weekly_plan.plan_id`, revision, or lifecycle row, so it remains available when that week's plan is replaced, archived, or absent; the table has no foreign keys.

Each user-week has at most one `content_md LONGTEXT NOT NULL` row with UTC `created_at` and `updated_at`; `PUT /api/{user}/weeks/{week_name}/feedback` uses the existing path-user authorization, is last-write-wins, preserves `created_at`, updates `updated_at` on every edit, normalizes whitespace-only content to `""`, and limits content to 256 KiB of UTF-8. `content` must be a string and unknown request fields are ignored for legacy-client compatibility. A feedback row makes the week discoverable, while `has_feedback` is true only when the normalized content is non-empty.

`GET /api/{user}/weeks` lists the union of weeks represented by active plans, activities, or feedback rows. `GET /api/{user}/weeks/{week_name}` joins the unique feedback row and that week's activities by `(user_id, week_start)`, returns only the active plan when one exists, and remains valid without one: the absent plan fields are `plan: null` and `structured: null`, while `activities` and `feedback` reflect any stored values and otherwise default to `[]` and `""`. All three sources absent returns `404`. The list returns only `has_feedback`; detail and PUT also return feedback content and timestamps, using `null` timestamps only when no feedback row exists.

`weekly_feedback.content_md` is the sole weekly-feedback body after cutover. Activity `sport_note` remains activity-level data and is not appended to it. The rollout migration uses a strict dry-run and atomic reviewed apply for the real-user allowlist in `src/migration/src/users.js`: migrate SQLite `weekly_feedback` rows first, preserving valid source timestamps, and import legacy `feedback.md` only for a user-week with no SQLite row. Legacy week suffixes are stripped only after strict Monday-to-Sunday validation; malformed identities, duplicate normalized weeks, or invalid timestamps block apply. Production activation is manual: after migration verification, enable the feedback PUT route together with both Go week readers, then retire runtime `feedback.md` append/sync/read paths. Until that activation, existing production compatibility paths remain live. Afterward there is no `feedback.md`/SQLite fallback or dual write.
